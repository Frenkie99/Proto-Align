## 一、当前设计阶段承接的产品定位

以下判断是本设计阶段始终遵守的上游背景，但仍请与产品定义对话的最新结论核对：

- 产品面向初阶 AI 产品经理，是公司内部使用的项目级 Agent。
- 产品不是一次性“AI 原型点评工具”，也不是完整项目管理平台。
- 核心产品对象是 Issue，原型是问题的承载和跨版本验证对象。
- 核心任务是推动问题从发现、理解、取舍、修改到验证和关闭。
- 问题来源包括客户反馈、研发反馈和 AI 主动发现。
- AI 推断的问题必须标记“AI 推断·待确认”。
- Agent 负责理解资料、关联证据、发现风险、提出建议和比较版本。
- 产品经理负责确认事实、处理冲突、做出取舍以及批准问题关闭。
- Agent 具有不显化的产品教练作用，但不能替用户做最终判断。
- 体验上像驻留在项目中的产品伙伴；MVP 技术上由用户主动触发运行。

## 二、设计阶段新增并已由用户接受的产品使用逻辑

### 1. 项目入口

- 页头“AI 客服回复助手”应是**单项目切换器 / 下拉框**，不是复选框。
- 一次进入一个项目上下文；项目之间的资料、问题和记忆必须隔离。
- 没有资料的新项目应显示空状态，先导入首批资料，再启动评审。

### 2. 两级输入入口

输入不应全部放在“关联证据”中，应分为两层：

#### 项目级「资料与输入」

- 导入原型版本：Figma 链接、可运行网页、HTML、PDF、截图；
- 上传项目资料：需求文档、PRD、合同、流程图、研发记录；
- 导入会议材料：会议音频、转写稿、会议纪要；
- 手动记录客户、售前、研发或产品负责人的角色反馈。

#### 问题级「添加 / 关联证据」

- 从项目资料中关联已有证据；
- 给当前 Issue 直接新增客户或研发反馈；
- 保留来源角色、时间和原文位置；
- 新反馈仍然是待验证主张，不能自动成为正式需求。

### 3. 原型与证据分开

- 原型版本是被评审对象；
- 客户、研发和业务资料是评审依据；
- 两者不应混成同一种上传物；
- Issue 只关联需要的证据，不复制整个项目资料库。

### 4. 问题与原型位置的对应

- 选择左侧 Issue 时，中间原型画布必须同步定位对应区域；
- 左侧选中问题的编号与画布标注使用同一橙红色，建立明确视觉对应；
- 橙红色只用于当前问题定位，不升级为普通业务状态色。

### 5. 输入到问题的暂定闭环

当前高保真原型演示了：

```text
录入角色反馈
→ 保存为项目资料中的待确认主张
→ Agent 复检
→ 生成待确认问题草稿
→ 产品经理确认事实并定位原型影响范围
```

这条流程是为了验证对象关系与交互是否成立。是否作为最终 MVP 主演示链，请由产品定义对话结合整体方案确认。

## 三、已选定的 UI 方向

用户已选择：**冰川蓝白＋黑的问题评审工作台**。

### 信息架构

- 顶部：项目切换、需求基线、版本记录、交付门槛、资料导入、启动复检；
- 左侧：按生命周期分组的问题列表和活动追踪；
- 中间：问题上下文画布，包含原型位置、问题标注、修改前后与关联证据；
- 右侧：Agent 解读、重要性、确认问题、验收条件、下一步建议、对话入口和结构化操作。

### 视觉规则

- 外层使用白色到浅冰蓝的单向环境渐变；
- 页面主色为白、浅冰蓝、清透青蓝、钴蓝和近黑；
- 模块内部不滥用渐变；
- 左中右可融合，但必须通过分隔线、标题栏、留白和列宽清楚区分；
- 保留较大圆角、轻量毛玻璃、细边界和克制阴影；
- 普通状态使用同一蓝色系的明度、描边和填充；
- 当前问题定位使用唯一的橙红色例外；
- 不使用来源不明的总分、虚构统计数字或装饰性 AI 星光。

该方向已经选定，后续开发不应重新生成三套设计或退回通用 AI Dashboard。
