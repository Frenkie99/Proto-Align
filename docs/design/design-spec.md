# 三方向高保真原型共同任务书

## 设计顾问复述

这次不是要给现有草稿“换一套更高级的皮肤”，而是验证三种不同的产品工作方式。目标用户是一位正在把 B 端 AI 功能原型交付研发的初阶 AI 产品经理。他面对的核心困难，不是缺少一句通用点评，而是客户反馈、研发约束和 AI 主动发现散落在不同资料中；问题和原型位置无法对应；修改后也很难证明问题是否真的被解决。因此，设计必须把 Issue 作为核心对象，让证据、原型、决定和验证条件形成闭环，同时让 Agent 像驻留在项目中的产品伙伴：它会检索、对照、发现风险和生成草稿，但事实确认、取舍及关闭权始终在产品经理手中。三稿必须用同一份业务信息，分别回答“从问题开始工作”“从证据开始调查”“由 Agent 带着完成一次评审”这三种心智模型，确保差异来自信息架构与交互，而不是表层样式。

## 共同场景

- 产品内部名：ProtoAlign / 原型对齐助手
- 当前项目：AI 客服回复助手
- 当前门槛：研发交付前
- 当前结论：暂不可交付
- 当前版本：V1；版本控件必须是下拉框，并允许选择 V1、V2、V3、V4，不用两个版本按钮。
- 使用者：初阶 AI 产品经理，当前为单人内部工具。
- 原型页面：客服工作台 / 回复生成区。
- 核心功能：客服输入用户问题后，AI 基于企业知识库生成候选回复，由客服确认后发送。

## 共用真实业务内容

### 问题一：知识库更新延迟没有被清楚告知

- 编号：ISS-014
- 来源：客户反馈
- 严重程度：阻塞交付
- 状态：处理中
- 关联：V1 / 客服工作台 / 回复生成区
- 影响：客服可能把基于过期政策生成的回复直接发给用户，造成误解与投诉。
- 客户会议纪要（7 月 28 日）：「知识库更新后，客服回复中的部分信息与实际政策不一致，用户没有被告知可能延迟，导致误解和投诉。」
- 研发评审记录（7 月 30 日）：「知识库同步为异步任务，更新完成时间不能保证；前端必须展示同步状态和最近更新时间。」
- Agent 判断：客户反馈与研发约束指向同一风险。V1 仅显示“基于知识库生成”，没有同步状态、最近更新时间或过期提示。
- 建议修改：在回复区域展示知识库同步状态和最近更新时间；资料过期或同步中时给出明确提示；高风险回复进入人工确认。
- 验证条件：V2 中能看到知识状态与最近更新时间；同步中或资料过期时出现明确提示；客服不能在未确认风险时直接发送。

## Agent 可见工作

只显示可核验的行动摘要，不展示思维链：

1. 已检索《7 月 28 日客户会议纪要》，定位到“知识库更新延迟”反馈。
2. 已检查 V1「客服工作台」，回复区未发现同步状态和最近更新时间。
3. 已对照《7 月 30 日研发评审记录》，确认异步同步属于已知技术约束。
4. 已生成问题草稿 ISS-014，等待产品经理确认事实和处理方式。

Agent 辅导语气应简短、具体，例如：「这不是单纯的提示文案问题。你需要先确认：资料过期时，客服是否仍被允许发送？这个决定会同时影响交互和验收条件。」

## 人的结构化动作

- 开始处理
- 发起澄清
- 延后
- 接受风险
- 标记待验证
- 关闭问题

任何关闭与接受风险操作都必须让用户看到依据或确认提示。AI 只能提出建议，产品经理做最终操作。

## 三个必须独立的设计方向

### 方向一：问题指挥台 Issue Command Center

- 入口：问题队列。
- 信息架构：问题列表是主导航；选择问题后同时看到原型定位、证据和决定；Agent 为右侧常驻伙伴。
- 任务交互：快速切换问题、查看关联证据、执行状态动作、切换版本验证。
- Agent 过程：可折叠“活动记录”，按检索、检查、对照、生成草稿展示工具结果。
- 视觉方向：成熟编辑台 / 调查桌，暖灰底、氧化朱红批注、细规则线，低圆角、高信息密度但留出呼吸。

### 方向二：证据调查图 Evidence Investigation Map

- 入口：证据与主张，不先展示传统 issue inbox。
- 信息架构：客户纪要、研发约束、原型缺口作为证据节点；它们汇聚成问题，问题再指向决定和验证条件。
- 任务交互：点击证据节点高亮关系、在关系图与原型定位之间切换、确认“事实 / 推断 / 待确认”。
- Agent 过程：表现为调查轨迹或证据链，用户能看到 Agent 用哪些材料构成问题。
- 视觉方向：功能主义网格（秒数轮盘结果第 17 项）——灰线分割、系统化文本、直接链接语义、几乎无悬浮卡片；以朱红作为关系与冲突标记。

### 方向三：引导式评审会 Guided Review Session

- 入口：一次需要完成的评审会，而不是完整工作台。
- 信息架构：围绕单个问题依次通过“理解问题 → 确认事实 → 做出取舍 → 定义验证”四个检查点；其他问题缩进队列或抽屉。
- 任务交互：用户在每一步回答一个关键问题并留下决定，最后形成可验证的问题记录。
- Agent 过程：Agent 是主持人，明确展示当前阶段、已调用资料、等待人的哪个确认；不能假装后台自主完成。
- 视觉方向：深色中性舞台 + 精密工业控制感，受 Teenage Engineering 功能主义启发；用区域、编号和机械式控件表达阶段，不用蓝紫霓虹、玻璃拟态或聊天气泡海洋。

## 原型要求

- 输出三个互不依赖的单文件 HTML，内含 CSS 和 JavaScript，不依赖网络资源。
- 固定首屏 1440×1024，能在浏览器中直接打开；视口变窄时允许侧栏折叠或横向滚动，但不能破版。
- 至少提供两类可操作反馈：例如问题/证据/步骤选择，版本下拉，Agent 活动展开，结构化操作后的状态变化。
- 可用纯 CSS / 内联 SVG 绘制“客服工作台”原型局部，不使用外部图片、品牌 Logo 或 emoji。
- 页面文案全部来自本任务书；不得创造用户数量、完成率、交付分数或成本节省等统计数字。
- 源码顶部用注释记录设计假设、核心交互与色彩论证。

## 真实产品参照（只提炼，不复制）

Linear 的官方文档证明“把客户请求连到具体 issue、保留原始消息与来源链接、通过视图筛选问题”是可工作的产品模式。本项目只借鉴其紧凑问题操作与证据邻近原则，不复制 Linear 的品牌外观；ProtoAlign 还必须进一步表现原型位置、AI 推断标识和跨版本验证。
