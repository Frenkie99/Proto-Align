# ProtoAlign｜原型对齐助手

> 面向初阶 AI 产品经理的项目级 Agent，以 Issue 生命周期为核心，帮助产品经理发现、理解、处理和验证影响 AI 产品原型交付的问题。

> **文档状态：唯一权威版本。** 产品定义、设计和开发均以本文件为准；其他文档只提供细节、历史或实现参考。若与本文件冲突，以本文件为准。

## 1. 项目背景与当前阶段

这是一个 AI 产品经理面试项目，用于展示产品思维与 AI 开发能力的结合。

面试官给出的原始背景只有：公司内部的初阶产品经理制作原型后，需要持续吸收客户和研发反馈，使原型逐步符合两方诉求。其余产品对象、流程、边界和实现均是本项目后续推导形成的方案。

当前已经完成：

- 核心产品定义与 MVP 主闭环；
- Agent 与人的职责边界；
- 高保真交互原型与选定视觉方向；
- 由高保真原型工程化得到的 Next.js 全栈工作台；
- SQLite 项目持久化、文本资料导入、静态网页导入与渲染后 DOM 采集；
- 原型采集质量诊断，以及重复初评 Run 的确定性比较与稳定性提示；
- 基于 `deepseek-v4-pro` 的真实工具型 Agent 初评与跨版本复检；
- Issue 证据、人工决定、状态历史、版本和 Agent 活动记录；
- 本地自动化测试与真实 DeepSeek 固定样例验证。

当前尚未完成：线上部署与鉴权、云数据库、PDF / OCR / 音频 / Figma 输入、多页面自动爬取和视觉模型理解。

当前版本已经形成可本地运行的纵向 MVP；下一阶段不再发散产品方向，优先进行部署适配、真实项目扩展验证和演示准备。

## 2. 已确认的产品定位

不要把产品定义为：

- 一次性 AI 原型点评或打分工具；
- 上传原型后输出通用检查清单的工具；
- 完整项目管理或研发管理平台；
- 自动生成、自动修改原型的平台。

正式定位：

> 一个驻留在 AI 产品项目中的问题闭环 Agent。它帮助初阶 AI 产品经理管理从客户反馈、研发约束和 AI 风险发现，到原型修改与交付验证的全过程。

产品形态：

> 以 Issue 为核心的项目评审工作台 + 对话式产品教练。

核心产品对象是 **Issue（问题）**，不是原型。原型是问题的视觉化承载与跨版本验证对象；项目上下文是 Agent 正确理解和持续工作的基础。

Agent 的体验像持续驻留在项目中的产品伙伴；MVP 技术上仍由用户主动触发运行，不伪装成后台持续自主执行。

## 3. 核心用户、场景与最终关口

### 核心用户

- 初阶 AI 产品经理；
- 当前 MVP 是单人内部工具；
- 客户、研发、售前和产品负责人不需要登录系统，也没有独立审批账号。

外部角色的结论由产品经理通过会议纪要、聊天记录、文档或手工记录写入系统。系统必须同时记录“谁在使用系统”和“结论来自谁”。

### 首发场景

一个 B 端 AI 功能原型在交付研发前的评审。

正式主演示使用用户此前真实开发的 AI 产品，从空白项目开始导入并由 Agent 实际分析。**AI 客服回复助手**仅作为 API 或外部项目不可用时的备用演示样例。

### 最终关口

MVP 以“原型是否达到研发可开工状态”为最终评审关口，同时把客户需求是否被正确承接作为必要检查维度。

- 客户侧检查：目标、范围、业务流程和使用诉求是否被正确承接；
- 研发侧检查：规则、状态、异常、数据和技术约束是否足够明确；
- 客户与研发反馈可以交叉、反复发生，不假设严格单向流程；
- Agent 给出就绪建议，产品经理确认最终结论。

一句话目标：

> 帮助初阶 AI 产品经理在原型交付研发前，将每个重要问题转化为有依据、有位置、有决定、有状态、可验证的处理闭环。

## 4. 核心价值与成立条件

产品解决的不是“没人告诉产品经理怎么改”，而是多源反馈在真实项目中可能分散、含糊、粒度不同、互相冲突，并跨越多个原型版本。

Agent 的必要性主要出现在：

- 反馈散落在会议、聊天、需求文档和研发评论中；
- 不同角色的说法存在冲突或权威边界不同；
- 反馈描述了现象，但没有定位原因或受影响页面；
- 一处修改会影响多个页面、业务规则或 AI 失败状态；
- 有些重要遗漏没有被任何角色主动提出；
- 新版本看似修改了页面，却没有满足原问题的验证条件；
- 多轮迭代后，修改原因、决定依据和历史问题失联。

Agent 的核心价值不是比人更有最终判断权，而是以较低成本持续维护资料、反馈、原型位置、决定和版本结果之间的关系。

如果最终效果只比“通用大模型 + 检查清单”略好，产品就没有成立。

## 5. 核心对象与关系

```text
Project 项目
├── Prototype Version 原型版本（被评审和比较的对象）
├── Source 项目资料（原始证据）
│   ├── 需求 / PRD / 合同 / 流程图
│   ├── 客户 / 售前 / 研发 / 产品负责人反馈
│   ├── 会议纪要 / 录音 / 转写稿
│   └── 决策记录与历史材料
├── Claim 结构化主张
│   ├── 目标 / 事实 / 需求 / 约束
│   ├── 承诺 / 建议 / 假设
│   └── 待确认项 / 冲突
└── Issue 问题
    ├── Evidence Link 关联证据
    ├── Prototype Location 版本 / 页面 / 区域
    ├── Decision 人的决定与理由
    ├── Verification Criteria 验证条件
    └── Status Event 状态与审计历史
```

必须遵守：

- 原型版本与评审依据分开管理；
- 反馈只是待验证主张，不天然等于正式需求；
- 原型只是当前解决方案，不天然等于事实；
- Issue 关联具体证据，不复制整个项目资料库；
- 所有关键判断能回到来源、角色、时间、版本和原文位置；
- AI 主动发现的问题必须标记“AI 推断·待确认”；
- 严重程度与判断可信度分开呈现。

## 6. 项目入口与两级输入

### 项目入口

- 页头项目名称是单选下拉切换器；
- 一次只进入一个项目上下文；
- 项目之间的资料、问题和记忆必须隔离；
- 无资料项目显示空状态，引导先导入首批资料或原型；
- 首个真实版本必须允许用户创建一个空白项目，再导入自己的 AI 产品和评审资料；不能依赖预置 Issue 才能完成演示。
- 预置的“AI 客服回复助手”只保留为无网络或准备不足时的备用样例，正式主演示优先使用用户此前真实开发的 AI 产品。

### 项目级“资料与输入”

产品长期应接收：

- 原型版本：可运行网页、HTML、PDF、截图，以及后续的 Figma / Axure；
- 项目资料：需求文档、PRD、合同、流程图和研发记录；
- 会议材料：会议纪要、音频和转写稿；
- 角色反馈：客户、售前、研发、产品负责人等人的原始表达。

每份资料至少保存：项目、来源角色、资料类型、时间、版本、原文位置和解析 / 确认状态。

### 问题级“添加 / 关联证据”

- 从项目资料中关联已有证据；
- 给当前 Issue 直接新增角色反馈；
- 保留来源、时间和原文位置；
- 新反馈仍是待确认主张，不能自动升级为正式需求；
- Issue 只引用与自身相关的证据片段。

### 首个真实版本的输入裁剪

第一条闭环必须真实支持：

- 项目名称、产品目标和被评审范围；
- 文本需求 / 会议纪要；
- 手工录入客户或研发反馈；
- 通过可访问 URL 导入一个真实运行的网页原型，并读取其渲染后 DOM / 页面结构；
- 通过单文件 HTML 或静态构建 ZIP 上传原型，作为本地导入方式；上传内容只按静态网页运行，不执行服务端代码；
- 至少两个原型版本。

随后再按优先级增加：可提取文本的 PDF、截图 OCR、音频转写、Figma / Axure 读取和真正的多模态视觉理解。未实现前不得在演示中宣称已支持。

## 7. Issue 来源、结构与生命周期

### 问题来源

- **客户反馈**：需求价值、范围与使用风险；
- **研发反馈**：实现约束、成本、依赖与交付风险；
- **AI 主动发现**：专业检查风险，必须标记“AI 推断·待确认”。

### Issue 最小结构

- 标题、类型、来源、严重程度、可信度和当前状态；
- 关联版本、页面、区域及修改前后变化；
- 支撑证据、来源角色、时间和原文位置；
- 对客户、用户或研发交付的影响；
- Agent 的判断依据和建议方向；
- 待澄清问题及结论来源角色；
- 修改后的验证条件；
- 产品经理的决定、理由和状态历史。

### 生命周期

```text
发现问题
→ 关联证据
→ 定位原型位置
→ 确认是否成立或存在冲突
→ 明确确认对象和处理方式
→ 修改原型或记录取舍
→ 导入新版本
→ 按验证条件复检
→ 已解决 / 已延后 / 已接受风险 / 重新打开
```

建议状态集合：

- AI 草稿 / 待确认；
- 待澄清；
- 待处理；
- 处理中；
- 待验证；
- 已解决；
- 已延后；
- 已接受风险；
- 重新打开。

状态规则：

- **已解决**：修改完成，并有证据表明验证条件已经满足；
- **已接受风险**：明确决定不修改，记录依据和影响；
- **已延后**：当前阶段暂不处理，后续版本必须重新检查；
- “决定不改”不能伪装成“已解决”；
- Agent 只能提出复检建议，不能自动关闭问题；
- 产品经理拥有系统内最终操作权，并负责记录外部角色的确认依据。

## 8. Agent 与人的边界

### Agent 负责

- 理解资料与角色反馈；
- 提取结构化主张并保留引用；
- 检索项目上下文并关联证据；
- 定位问题对应的原型版本、页面和区域；
- 发现遗漏、冲突、AI 产品风险和研发交付风险；
- 提出澄清问题、处理建议和验证条件；
- 比较新旧版本并给出“疑似已解决 / 未解决 / 无法判断 / 引入新问题”；
- 解释为什么需要检查及成熟产品经理通常还会考虑什么；
- 记录可核验的工具行动与结果。

### 人负责

- 确认事实与需求 / 约束基线；
- 判断反馈是否成立及由谁拥有事实确认权；
- 处理客户、产品与研发之间的冲突；
- 决定处理、澄清、延后或接受风险；
- 记录外部角色结论及依据；
- 批准问题关闭和最终研发交付。

必须保留四个人工确认节点：

1. 需求与约束基线确认；
2. 冲突与重要取舍确认；
3. 外部角色结论记录与确认；
4. 问题关闭及最终交付确认。

Agent 的产品教练作用嵌入真实任务，不单独设置课程模块。对话用于解释、追问和辅导；结构化操作负责状态改变。

界面只展示“检索了什么、调用了什么工具、得到什么结果、正在等待什么确认”，不展示隐藏思维链。

## 9. 输出与研发就绪结论

核心输出是可持续处理的 Issue，不是一篇一次性长报告。

辅助输出包括：

- 当前评审摘要与主要阻塞项；
- 待澄清事项及建议询问角色；
- 新旧版本的逐问题复检结论；
- 结合当前问题的嵌入式产品指导；
- 研发交付前检查结果。

研发就绪建议只使用：

- **暂不可交付**：仍有未解决阻塞问题；
- **有条件可交付**：存在已接受或明确延后的风险；
- **可以交付**：阻塞问题均有验证依据并完成处理。

不用来源不明的总分、进度条或完成率制造虚假确定性。Agent 给出建议，产品经理最终确认。

## 10. MVP 主闭环与演示方案

正式主演示链已确定为：**跨版本 Issue 验证闭环**。

```text
创建一个不含预置 Issue 的空白项目
→ 导入用户此前真实开发的 AI 产品 V1（URL、单文件 HTML 或静态构建 ZIP）
→ 补充产品目标、文本资料及客户 / 研发反馈
→ Agent 提取待确认主张并由产品经理确认基线
→ Agent 生成三条以内有证据的高价值 Issue
→ 产品经理选择一个 Issue 处理并记录决定
→ 导入 V2 或更高版本
→ Agent 按该 Issue 的验证条件复检
→ 产品经理确认已解决、延后、接受风险或重新打开
→ 形成研发就绪建议
```

问题来源应至少覆盖客户反馈、研发反馈和 AI 主动发现各一类。

“新增角色反馈 → Agent 生成待确认问题草稿”保留为辅助演示链，用于证明项目上下文会持续吸收新信息，但不与跨版本主线争抢演示重心。

演示重点不是生成几十条建议，而是证明：

- 三条以内有证据的重要问题；
- 至少一条完整问题生命周期；
- V1 到后续版本的真实复检；
- Agent 建议与人工确认边界；
- 工具调用和项目记忆是真实的，而非预设播放。
- 演示结果由本次导入内容动态产生，项目中不得预置主演示所需的 Issue 或复检结论。

## 11. MVP 范围

### 必须具备

- 创建空白项目、项目切换与项目上下文隔离；
- 真实 AI 产品的 URL、单文件 HTML 或静态构建 ZIP 导入；
- 项目级资料输入和问题级证据关联；
- 文本资料与可运行网页 DOM 的真实解析；
- 结构化主张抽取和原文引用；
- 人工确认需求 / 约束基线；
- 三条以内高价值 Issue 草稿；
- Issue 与版本、页面、区域和证据的关联；
- 处理、澄清、延后、接受风险、待验证和关闭；
- 导入新版本并按验证条件复检；
- 决定历史、Agent 行动记录和项目持久记忆；
- 研发就绪建议。

### 暂不包含

- 自动修改 Figma、Axure、网页或代码；
- 理解任意复杂动态交互；
- 代替客户、产品负责人或研发做最终判断；
- 完整项目排期、资源管理和研发工时估算；
- 完整多人协作、组织权限和通知系统；
- 覆盖所有行业的专业合规规则；
- 大量第三方系统集成；
- 后台持续自主运行；
- 跨项目个人成长画像；
- 自动发送客户或研发消息。

## 12. AI 产品专项评审维度

由于被评审对象是 AI 产品，评审除通用需求和研发交付外，还应检查：

- AI 能力边界是否向用户表达；
- 知识、数据或答案依据是否可追溯；
- 无法回答、低置信、超时和错误结果如何兜底；
- 人是否保留必要的编辑、拒绝和确认权；
- 是否存在反馈入口和后续效果评估条件；
- 数据权限、隔离、隐私、延迟和成本约束是否被考虑。

MVP 不深入模型训练、提示词优化和完整算法评测体系，只检查这些能力是否在产品流程和交付规格中得到承接。

## 13. 已确认的 UI 与交互方向

唯一视觉方向：**冰川蓝白＋黑的问题评审工作台**。不重新退回三方向探索，也不改成通用 AI Dashboard。

主参考：

- 高保真原型：`prototypes/current/detailed-workbench.html`；
- 选定截图：`prototypes/current/blue-black-deepened.png`；
- 方向记录：`docs/design/direction-approved.md`；
- 色彩细则：`docs/design/color-system-v3.md` 的“方案一”。

若 `docs/design/DESIGN.md` 中的暖灰 / 朱红基础探索与选定方向冲突，以本节、`docs/design/direction-approved.md` 和选定截图为准。

### 信息架构

- 顶部：项目切换、需求基线、版本记录、运行比较、交付门槛、资料导入与启动复检；
- 左侧：按生命周期分组的 Issue 列表与活动追踪；
- 中间：问题上下文画布，展示原型位置、证据、版本和修改前后；
- 右侧：Agent 解读、重要性、确认问题、验证条件、建议、对话和结构化操作。

### 交互规则

- 项目选择使用单选下拉框；
- 原型版本使用可扩展下拉框，不写死为 V1 / V2 双按钮；
- 选择 Issue 后，中间画布同步定位对应区域；
- 左侧当前 Issue 与画布定位区域使用同一浅蓝填充和蓝色描边，不显示编号或悬浮图钉；
- 对话不直接改变最终问题状态；
- 状态变化必须由结构化操作触发并记录理由；
- 体验像驻留 Agent，但每次实际运行由用户点击触发。

### 视觉规则

- 最外层使用白色到浅冰蓝的单向环境渐变；
- 主页面使用白、浅冰蓝、清透青蓝、钴蓝与近黑；
- 模块内部不滥用渐变；
- 通过分隔线、标题栏、留白和列宽区分三栏；
- 使用较大圆角、轻量毛玻璃、细边界和克制阴影；
- 普通状态以蓝色系明度、填充和描边表达；
- 当前 Issue 与原型位置沿用选定 HTML 的蓝色选中态，不额外引入橙红色强调；
- 不使用虚构统计、装饰性 AI 星光、总分或伪造思维链。

## 14. 已确认的 Agent 技术架构

当前实现决策：

- Web 与 API：Next.js + TypeScript；
- Agent Harness：OpenAI Agents SDK TypeScript；
- 核心模型：DeepSeek V4 Pro，使用 DeepSeek 开放平台 API 余额；
- 接入方式：通过 OpenAI 兼容 Chat Completions 和可替换 Provider 层接入；
- Agent 数量：MVP 一个 `Prototype Review Agent`，不为展示复杂度拆成多 Agent；
- 编排方式：确定性的外层问题闭环 + 阶段内受约束的 ReAct 式工具循环；
- 工具调用：直接函数工具调用，最大运行轮数默认 8；
- DeepSeek thinking mode：MVP 默认关闭，避免工具调用中 `reasoning_content` 兼容风险；
- 输出校验：Zod 约束工具参数和结构化输出；
- 本地持久化：SQLite；
- 部署持久化：不能依赖无持久磁盘的本地 SQLite，生产数据库供应商待部署前确定；
- 检索：本地文本切分与关键词 / FTS 检索，不依赖 OpenAI File Search；
- 追踪：关闭 OpenAI 云端 tracing，应用自己记录 Agent Run 和工具行动事件；
- 密钥：只使用服务端 `DEEPSEEK_API_KEY`，不得提交 Git 或暴露给浏览器。
- 原型采集：优先用 Playwright 打开在线或本地静态网页，提取渲染后 DOM、可见文字、交互控件、页面 URL 和稳定定位信息；首版不执行用户上传的服务端代码。

### 外层 Harness

```text
导入资料
→ 建立 / 更新项目上下文
→ 评审当前原型版本
→ 生成人工可确认的 Issue
→ 记录产品经理决定
→ 导入新版本
→ 复检历史 Issue
→ 形成研发就绪建议
```

### Agent 自主范围

Agent 可自主决定：检索哪份资料、查看哪个原型页面、是否继续查找证据、是否发现冲突、是否需要澄清，以及现有证据是否足以创建问题草稿。

Agent 不得自主决定：把反馈升级为正式需求、接受风险、关闭问题或宣布最终交付。

### MVP 工具集合

- `search_sources`：按关键词和来源筛选项目证据；
- `inspect_prototype`：读取可运行网页的 DOM、控件、文字、状态和位置；
- `list_prototype_pages`：列出当前原型可访问页面和已采集状态，供 Agent 决定检查范围；
- `compare_versions`：围绕指定 Issue 对照新旧版本；
- `get_issue_context`：读取问题、证据、决定和历史状态；
- `save_claim_draft`：保存带原文位置、等待人工确认的结构化主张；
- `save_issue_draft`：保存 AI 生成的问题草稿和验证建议；
- `save_verification`：保存跨版本复检建议与差异证据；
- `request_clarification`：证据不足时向产品经理提出具体问题。

DeepSeek V4 Pro 当前按文本模型使用，不能宣称直接理解任意截图。原型读取采用适配层：网页使用 DOM；PDF 使用文本提取；截图使用 OCR；未来再接入视觉模型、Figma 或 Axure，不改变上层 Issue 与 Agent 架构。

## 16. 真实 Agent 开发计划与验收

前后端按一条纵向闭环同步开发，不先做只有视觉的空壳。

**实现状态（2026-08-06）：** 里程碑 A、B 已在本地完成；初评、失败路径和 V1 → V2 复检均已用真实输入验证。线上部署及更多输入适配仍不属于已完成能力。

### 里程碑 A：真实初次评审闭环（首夜优先）

1. 建立 Next.js + TypeScript 前后端工程、服务端环境变量检查和 SQLite 数据层；
2. 用户创建一个没有预置 Issue 的空白项目；
3. 用户填写产品目标，并导入文本资料与真实网页 V1；
4. 系统采集并保存渲染后 DOM、可见文字、控件和页面位置；
5. `deepseek-v4-pro` 通过 OpenAI 兼容 Chat Completions 接入 OpenAI Agents SDK；若兼容层出现阻断，保留同一工具协议并使用自建受限 Agent Loop，不退化成写死 Workflow；
6. Agent 根据当前输入自主选择并真实调用 `search_sources`、`list_prototype_pages` 和 `inspect_prototype`；
7. Agent 输出三条以内带原文或 DOM 引用、原型位置、影响和验证条件的 Issue 草稿；
8. 页面展示真实 Agent Run、工具名称、参数摘要、结果摘要、耗时和失败状态；
9. API 或工具失败时明确显示失败，不播放预设成功结果；
10. 刷新页面后项目、资料、Agent Run 和 Issue 草稿仍然存在。

### 里程碑 B：人工处理与跨版本验证（次日完善）

1. 产品经理确认或修正需求 / 约束基线；
2. 产品经理确认 Issue，选择处理、澄清、延后或接受风险并记录理由；
3. 导入 V2 或更高版本并采集真实 DOM；
4. Agent 读取 Issue、证据、处理决定和两个版本，调用 `compare_versions`；
5. 每个 Issue 只输出“疑似已解决 / 未解决 / 无法判断 / 引入新问题”，并引用版本差异证据；
6. Agent 不得自动关闭问题，由产品经理进行最终确认；
7. 形成研发就绪建议和完整状态记录。

### 真实 Agent 的硬性验收标准

- 删除全部预置 Issue 后，仍能从新导入的真实项目生成问题；
- 修改需求或网页内容后，工具结果与 Issue 必须随输入变化；
- 至少一次运行由模型自主选择并连续调用两个不同工具，工具结果会回到模型并影响下一步；
- 每条 Issue 至少关联一个可打开的资料引用或 DOM 位置，不允许只有泛化建议；
- 断开 `DEEPSEEK_API_KEY` 后运行必须失败，不得回退到固定问题或定时动画；
- 活动记录必须来自真实 Agent 事件，不得预写“已检索”“已扫描”等成功文案；
- 相同固定样例重复运行时，关键证据和核心问题保持基本稳定；
- 同项目两个已完成初评可比较共同主题、独有问题、证据与严重程度变化；稳定性结论必须标记“待人工确认”；
- 只有人工操作可以确认基线、接受风险和关闭 Issue。

完成里程碑 A 后，可以诚实称为“可运行的 Agent MVP”；完成里程碑 B 后，才能证明本产品定义中的问题闭环 Agent，而不仅是通用网页点评器。

## 17. 当前原型与真实开发边界

`prototypes/current/detailed-workbench.html` 仍是已经确认的 UI 与交互基线，本身不是 Agent。根目录 Next.js 应用是依据该基线工程化的可运行 MVP，不重新定义产品或另做视觉方向。

当前应用已实现：

- 从没有预置 Issue 的空白项目开始；
- 创建和切换项目，保存产品目标与评审范围；
- 手工录入或导入 TXT / Markdown / HTML 文本资料；
- 通过 URL、单文件 HTML 或静态构建 ZIP 导入原型版本；
- 在受控浏览器中采集渲染后 DOM、可见文字、控件、稳定选择器和截图；
- 将采集结果区分为可评审、疑似登录页、加载空壳和采集失败；非可评审版本不会启动 Agent；
- 由 DeepSeek Agent 自主调用资料检索、原型检查、问题保存和版本比较工具；
- 保存带原文 / DOM 证据、原型位置和验证条件的 Issue 草稿；
- 由产品经理确认基线、记录处理依据、接受风险或关闭问题；
- 导入新版本后生成带差异证据的复检建议；
- 持久化项目、资料、版本、问题、决定、复检和真实 Agent 活动记录；
- API、模型或工具失败时保存并展示真实失败，不生成虚拟成功结果。
- 比较同项目两个已完成初评 Run 的共同 / 独有主题、证据和严重程度差异，并显示可复算且待人工确认的稳定性提示。

当前应用尚未实现：

- PDF 解析、OCR、音频转写和 Figma API；
- 用户认证、组织权限、云数据库和线上部署；
- URL 站点的多页面自动爬取与登录态采集；
- 任意复杂原型的视觉 / 交互理解；
- 后台自主运行和并行批量评审；
- 真实研发交付包导出。

本地 SQLite 数据、上传文件和截图均保存在 `data/`，并已排除在 Git 之外。开发不得用写死结果或定时动画冒充未实现能力。

## 18. 可信度与最高风险

最危险的 Agent 错误是**错误关闭**：实际仍存在关键需求、冲突或失败流程，Agent 却建议问题已解决或原型可以交付。

其他主要风险：

- 编造需求或错误理解资料；
- 把客户、售前或研发反馈直接当成正式需求；
- 把 AI 推断包装成事实；
- 使用过期资料评审新版本；
- 只看页面有变化就判断问题解决；
- 原型版本与评审依据混在同一个上传对象；
- 仅凭 OCR 或截图假装理解复杂交互；
- 生成大量低价值问题增加负担；
- 泄露合同、客户资料和内部方案；
- 为了表现 Agent 而展示伪造思维链或后台自主运行。

可信度机制：证据引用、来源角色、时间版本、事实 / 推断区分、严重程度与可信度分离、人工确认节点、状态审计和固定样例评测。

## 19. 项目交付形式与本地运行

面试交付建议包含：

- 可直接体验的在线网页链接；
- GitHub 仓库链接；

不需要购买独立域名，部署平台生成的链接即可。GitHub 仓库不得包含 API Key、客户数据或其他秘密。

### 本地运行

运行环境要求 Node.js 20.9 或更高版本。首次安装：

```bash
npm install
npx playwright install chromium
cp .env.example .env.local
```

在 `.env.local` 中填写自己的 `DEEPSEEK_API_KEY`。`DEEPSEEK_BASE_URL` 默认为 `https://api.deepseek.com`；模型固定使用 `deepseek-v4-pro`，密钥只由服务端读取。

启动开发环境：

```bash
npm run dev
```

打开 `http://localhost:3000`。生产构建与启动：

```bash
npm run build
npm start
```

### 验证命令

```bash
npm run typecheck
npm test
npm run test:e2e
npm run verify:prototype
npm audit --audit-level=high
```

端到端测试使用隔离的临时数据库并故意不提供模型密钥，以验证失败会如实显示且不会生成预置 Issue。真实模型验收需要另行配置有效的 DeepSeek 密钥，并从界面导入至少一份文本资料和一个已采集的原型版本。

### 已知限制

- 当前为单机单用户 MVP，SQLite 不适合多实例并发部署；
- URL 导入只采集传入的首个公开页面；系统会识别疑似登录页和加载空壳，但不会处理登录凭据、Cookie 或多页流程，后续安全边界见 `docs/architecture/authenticated-multipage-capture.md`；
- 上传原型只运行静态 HTML / CSS / JavaScript，阻断其外部网络请求，不执行用户提供的服务端代码；
- 文本资料当前只支持手工录入、TXT、Markdown 和 HTML，单文件上限 2 MB；
- 原型上传当前支持单文件 HTML 或静态 ZIP，上传上限 25 MB，解压上限 100 MB；
- DeepSeek 运行在请求内同步完成，受 8 轮工具循环和工具超时限制；每次初评优先保存一条最高价值 Issue；
- 复检只比较 DOM 文本与控件差异，不包含截图视觉理解；
- 没有有效 API Key、模型返回非法结构或任何工具失败时，运行会失败并保留审计记录，不回退到虚拟结果。

## 23. 给新开发任务的启动指令

